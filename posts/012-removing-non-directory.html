Removing non-directory

2026‑11‑28   Yu Hsien Fang

This one is older than the others. It happened in August and I did not write it up then. I no longer have the terminal output from that day. What I have is a note I wrote the same evening, and npm, which is the same version and still does it.

The job

A repository of mine lived inside a folder that iCloud Drive syncs. When a build rewrites node_modules quickly, iCloud can end up making conflict copies, directories with 2 appended to the name. TypeScript loads every package it finds under node_modules/@types, the copies included, and fails on each one with error TS2688, "Cannot find type definition file". The project's local verification script exited non-zero. Nothing in the code was wrong.

My agent applied a workaround. A folder whose name ends in .nosync is left alone by iCloud Drive, so the agent moved the packages into node_modules.nosync and put a symbolic link named node_modules in its place, pointing at it. Then it reinstalled and ran the verification script again. It passed.

About two hours later the agent looked again and found the workaround gone. My note from that evening (translated):

The first version, .nosync plus a symlink, was disproved by my own test within two hours. npm install replaces the node_modules symlink with a real directory, with no error message. The first passing verify actually ran on a real directory whose protection had already been removed.

What npm does

Here is the same thing today, on a project with one dependency, installed from a local tarball so nothing touches the network. Before:

$ ls -ld node_modules
lrwxr-xr-x@ 1 ysfang  staff  19 Nov 28 16:19 node_modules -> node_modules.nosync
$ ls node_modules
tinypkg

The package is installed and reachable through the link. Then:

$ npm install --no-audit --no-fund --offline
npm warn reify Removing non-directory <tmp>/app/node_modules

added 1 package in 86ms
$ echo $?
0
$ ls -ld node_modules
drwxr-xr-x@ 4 ysfang  staff  128 Nov 28 16:19 node_modules
$ test -d node_modules && echo "node_modules is there"
node_modules is there

npm found a symbolic link where it expected a directory, deleted it, created a real directory and installed into it. It said so. The warning went to stderr and the summary line went to stdout, so anything that keeps only stdout, or only the last line, sees this:

$ npm install --no-audit --no-fund --offline 2>&1 | tail -1
added 1 package in 87ms

That run was in a fresh copy of the project, and npm had replaced the link there too. "added 1 package" on a project where the package was already installed is itself a hint, but only if you know to read it as one.

This is deliberate. The function that does it in npm's installer, @npmcli/arborist 9.4.3, lib/arborist/reify.js, sits under the comment // do not allow node_modules to be a symlink. npm ci goes further. Its documentation says "If a node_modules is already present, it will be automatically removed before npm ci begins its install", and with a link that means the directory it points to is emptied first:

$ npm ci --no-audit --no-fund --offline 2>&1 | tail -1
added 1 package in 87ms
$ ls -A node_modules.nosync | wc -l
       0

I ran the same fixture through two other package managers. With pnpm 10.27.0 and bun 1.3.11 the link was still there afterwards. So this is npm's choice. Whether a link survives depends on which tool runs next.

What I got wrong

I accepted the workaround because the check passed right after the reinstall. That check could not have failed at that moment. The verification script looks for the symptom, type errors from conflict copies. The reinstall had just written a fresh node_modules, and copies only appear after iCloud has had a chance to sync a tree that is being rewritten. My note says only that the verify ran on the real directory. I think the reason it passed is that obvious one: there were no copies yet, with or without the workaround. A pass at that point said nothing about whether the fix worked.

I also checked the fix right after setting it up, and not after the next thing that was going to touch it. The workaround lived inside node_modules, which npm owns and rebuilds. A change made inside a path that another tool rebuilds lasts until that tool runs again. I had set it up, installed, and verified, in that order, and the install was the step that took it apart.

I read the exit code and the summary. I do not know whether the agent's captured output showed the warning that day. Today the warning goes to stderr and the command exits 0.

How it was caught

By looking at the mechanism instead of the symptom. The fix had two parts: node_modules should be a link, and the packages should be in node_modules.nosync. The second check found node_modules.nosync empty and node_modules a real directory. Neither of those needs a type checker or iCloud to answer.

It also needed a way of looking that does not follow the link. ls node_modules, test -d node_modules, and Node's module resolution all go through a symbolic link to whatever it points at, so they work the same whether the link is there or npm has replaced it. Only views of the link itself, ls -ld, test -L, lstat, show the difference.

What we did instead

We moved the whole repository out of the synced folder and left a symbolic link at its old path, so every existing reference still resolves. npm does not look above the project root, so it never touches that link. The same check that catches the first fix passes this one; the output is below.

The rule I installed

  • Check a workaround after the next run of the tool that owns the path, not after you set it up. If the workaround lives in node_modules, .venv, build/ or anything else a tool regenerates, run that tool once and then look.
  • Check the mechanism, not the symptom. A symptom check that runs right after a step that clears the symptom passes whether or not the fix works. Here the mechanism check is two lines: test -L node_modules, and the packages are in the place you meant them to be.
  • Read stderr on runs that exit 0. npm put the only true sentence of that run in a warning.

Run it

checks/012/linkguard.py runs a command and reports whether it changed what the paths you name are: missing, a file, a directory, or a symbolic link and where it points. It describes each path with os.lstat and os.readlink before and after, and does not use the command's output or exit code to decide anything. Before judging your command it runs five controls in a temp directory: a link replaced by a directory, a command that does nothing, a file written through the link, a link pointed somewhere else, and a link replaced by a command that then fails. If they do not come out as expected it stops. checks/012/demo.sh builds the toy project used above, offline, and prints its path.

On npm:

$ python3 linkguard.py node_modules -- npm install --no-audit --no-fund --offline
control OK    link replaced by a directory, exit 0: exit 1
control OK    nothing happens: exit 0
control OK    a file is written through the link: exit 0
control OK    link pointed somewhere else: exit 1
control OK    link replaced, command fails: exit 4
npm warn reify Removing non-directory <tmp>/app/node_modules

added 1 package in 85ms
command exit 0
  CHANGED node_modules: link -> node_modules.nosync  =>  directory
$ echo $?
1

Exit 1 means a path changed while the command reported success. Exit 4 means it changed and the command failed. On the fix we kept, run from inside the linked repository path:

$ python3 linkguard.py <tmp>/repo-link node_modules -- npm install --no-audit --no-fund --offline
...
up to date in 82ms
command exit 0
  kept    <tmp>/repo-link: link -> <tmp>/app
  kept    node_modules: directory

On the toy project the whole run, npm included, takes about 0.2 seconds.

I broke it twelve ways with checks/012/mutate.py and ran each version against seven commands with known answers, including npm, pnpm, a command that fails after replacing the link, and a dangling link that gets removed. Ten changed at least one answer. Two did not: switching off the control enforcement, and removing the check that the fixture link was made. On a healthy machine those behave exactly like the original, so these tests cannot tell them apart. I also tried the mistake this entry is about: describing paths in a way that follows the link, with the fixture check and the controls both switched off so nothing else stops it. Against npm it then prints kept node_modules: directory and exits 0.

I ran this on macOS 27.2 with npm 11.13.0, Node 24.9.0, pnpm 10.27.0, bun 1.3.11, and Python 3.14.6 and 3.9.6. I have not run it on Linux.

This is a catalogue of cases where a tool reported success, or reported nothing, and I believed it. Each entry gets the date, the commands, and the shape of the error. More will follow.
