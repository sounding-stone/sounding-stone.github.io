Four lines from one night. The first came from the CI log of a failed deploy, the next two from the agent checking locally, and the fourth from the same CI log as the first, 25 lines above it. All four are accurate. The agent acted on the first one.

69 passed (10.0m)

2026‑10‑02   Yu Hsien Fang

At two in the morning an agent was shipping a frontend change for me. The deploy workflow runs the end-to-end suite (Playwright, 87 tests, one worker) before it deploys. The suite failed, so nothing deployed. That part worked as designed.

The agent's job was to find out why. It was my agent and my deploy, so what follows is written as my mistake.

What was on the screen

The failed job's log is 4,079 lines, most of it output from the test server. The agent pulled it with gh run view --log-failed and filtered it five times in two minutes. The filters, run again today on the same log:

  1. grep -E "✘|failed|Error:|expect\(|Timeout|›" | head -30 matched 87 lines. The first 30 were all passing tests (› appears on every test line). The one ✘ was match 86. Timeout does not match Timed out.
  2. grep -E "✘|[0-9]+ failed|[0-9]+ flaky|[0-9]+ passed" | head -12 matched 3 lines: a server log line containing 0x6d8becd0 failed with error, then 69 passed (10.0m), then the ✘. This is the one that had the answer on screen.
  3. sed -n '/✘ 71/,/…/p': everything from the ✘ downward.
  4. A grep that did include Timed out, piped to head -25. It matched 1,065 lines. All 25 shown were JSON log lines whose key names contain Locator. The Timed out lines were matches 1,056 and 1,057.
  5. awk '/✘ 71/{f=1} f': from the ✘ downward again. What it printed (test name redacted): 
      ✘  71 [chromium] › <spec A> (3.2s)
⚠  Script exited unsuccessfully (code 1)
Error: Script "npx playwright test" exited with code 1
##[error]Process completed with exit code 1.

Between the fourth and fifth filter it ran the failing test 20 times locally:

  20 passed (35.1s)

After the fifth, its conclusion, paraphrased from its log: the CI output ends right after the ✘, CI probably runs with --max-failures, and no error message was printed. It tried to download the run's artifacts (there were none), then ran the whole suite locally with the CI settings:

  86 passed (2.9m)

Fails in CI, passes locally twenty times out of twenty: it read that as a timing flake, and wrote a brief for a second agent to investigate it. Find out whether the test's timing assumption was wrong or the product had a race; fix it by waiting on events (no sleeps, no looser assertions, no retries); add a step that keeps traces when the suite fails.

This is the part of the same log that none of the five reads showed, 25 lines above the ✘ (timestamps are UTC; the 18 lines of server output between the summary and the ✘ are omitted):

2026-09-28T18:04:18.1338119Z   ✘  71 [chromium] › <spec A> (3.2s)

The config had globalTimeout: 10 * 60_000. The suite needs about 2.9 minutes on my machine; on the CI runner it ran out of ten. Playwright stopped, said so in English, counted what had and had not run, and pointed upward (“see above for details”). The ✘ arrived 1.9 seconds after the summary, for the test that was still running when the clock stopped. The summary's three counts (1 + 17 + 69) already add up to the 87 planned tests without it.

Nothing in this log is false. The ✘ is a real mark on a real test. 20 passed and 86 passed (2.9m) are true. The cause was printed once, in plain words, above the only line the agent went looking for.

What I got wrong

  • I let the red mark set the question. Every filter after the first was built around ✘ 71: grep for its name, print from it downward. A summary is printed once, at the end of the run; the mark for a test killed by the global timeout is printed after it. Reading down from the mark is reading past the answer.
  • I had 69 passed (10.0m) in front of me and didn't read it. 69 is not 87, and 10.0m is a round number. Either one was enough.
  • | head let the noise decide what I saw. Twice the pattern was close enough; the output limit cut the matching line, behind 30 passing tests in one case and 1,055 JSON lines in the other. A count first (grep -c) would have shown 1,065 matches where I expected a handful.
  • I treated “passes locally” as evidence about CI. The local runs answered “does this test pass on its own” and “does the suite pass here”. The CI question was about time, and the durations were right there: 35 s, 2.9 m, 10.0 m.
  • I paid for it with another agent's round. The second agent changed how the test waits and added trace upload. Neither change was harmful. Neither was the fix. A third agent reviewing that work wrote, paraphrased, that the explanation did not match how the page actually gates rendering and that it could not claim the CI root cause had been found. The work merged; its tests were green.

From the agent's “no error was printed” to the pull request that raised the limit: 46 minutes.

What caught it

A different test, failing after 487 ms, at the same 10.0 minutes. One failure points at a test. Two failures on unrelated tests, stopping at the same wall-clock time, point at a clock. The agent grepped the config for timeouts, found globalTimeout: 10 * 60_000, and raised it to 15 minutes.

This was luck more than method. If the second run had happened to finish in 9 m 58 s, the flake story would have looked confirmed.

Reproducing it

You need Node and npm i -D @playwright/test. No browser is needed. I used Playwright 1.59.1, the version in that project's lockfile, on Node 24.9.0.

playwright.config.js:

module.exports = { testDir: './tests', workers: 1, reporter: 'list', globalTimeout: 10_000, timeout: 30_000 };

tests/s.spec.js: twelve tests of one second each, against a ten-second limit:

const { test, expect } = require('@playwright/test');
for (let i = 1; i <= 12; i++) {
  test('step ' + String(i).padStart(2,'0'), async () => {
    await new Promise(r => setTimeout(r, 1000));
    expect('ok').toBe('ok');
  });
}

npx playwright test, exit code 1:

Running 12 tests using 1 worker

  ✓   1 tests/s.spec.js:3:3 › step 01 (1.0s)
  …
  ✓   9 tests/s.spec.js:3:3 › step 09 (1.0s)
Timed out waiting 10s for the test suite to run
Timed out waiting 10s for the teardown for test suite to run

  3 did not run
  9 passed (10.0s)
  2 errors were not a part of any test, see above for details

One difference from CI: locally I could not get the trailing ✘ to appear, with or without a browser page in the test, with or without CI=1 and retries: 1. Locally the interrupted test is only counted under “did not run”. I don't know what in the CI setup prints the late ✘. The summary block is the same in both.

What generalises

  • Read the summary block before any mark. Check that its counts add up to the number of planned tests (Running 87 tests) and that the duration isn't sitting on a configured limit. A run that stops at exactly 10.0m when globalTimeout is 10 minutes has told you its cause.
  • Count before you limit. grep -c first; if the count is not what you expected, the pattern is matching something else, and head will show you that something else.
  • “Passes locally” is a claim about local conditions. When CI and local disagree, compare durations, not pass counts.

The check

suite_cap.py reads a Playwright list-reporter log, raw or with GitHub Actions prefixes, and answers from the summary block only. It never looks at ✘.

$ python3 suite_cap.py ci-run-1.log
planned: 87  skipped: 1  did not run: 17  passed: 69  wall: 10.0m
verdict: SUITE_TIMEOUT (suite clock 600s ran out; 17 did not run)
$ echo $?
2

Exit codes: 0 pass, 1 test failure, 2 suite timeout (test failures, if any, reported alongside), 3 no summary found. Exit 3 means the script will not guess: a log cut off before the summary is not treated as a failure of whichever test it ends on.

10 mutants, 9 caught, 1 survived

Three of the mutants are the five reads above, written as code: verdict from the first red mark, reading from the mark downward, and head -30. The survivor keys the timeout on the second “Timed out” line instead of the first. Playwright printed both lines together in every run I have, so the controls can't tell the two apart. I'm leaving it as a known gap rather than writing a fixture Playwright doesn't produce.

On the two real CI logs (not published), the script returns SUITE_TIMEOUT both times: 17 did not run in the first, 1 in the second.
