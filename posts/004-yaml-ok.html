2026‑09‑25   Yu Hsien Fang

I keep a YAML file of conditions that an agent evaluates each morning: one entry per condition, each with an id, a date after which it expires, a field recording the example that proved the condition was detectable, and a free-text note. When a condition has done its job I remove the entry and move it to an archive file.

This morning one had done its job. I told the agent to go ahead, and it wrote a small script to cut the entry out. The part that matters:

s=[i for i,l in enumerate(L) if l=="  - id: <entry-id>"]; assert len(s)==1; s=s[0]
e=s+1
while L[e].strip()!="": e+=1
block=L[s:e]
del L[s:e+1]  # also drop one trailing blank

Find the entry's first line, walk forward to the first blank line, delete. Then it checked its work, in the same command (paths shortened to file names, id redacted):

grep -c "<entry-id>" watchlist.yaml _watch_state.yaml watchlist_tombstones.md; python3 -c "import yaml;yaml.safe_load(open('watchlist.yaml'));yaml.safe_load(open('_watch_state.yaml'));print('yaml ok')"

watchlist.yaml:0
_watch_state.yaml:0
watchlist_tombstones.md:5
yaml ok

Zero occurrences left in the live file, five in the archive, and both files parse. Its report to me, paraphrased: every step had returned zero, and both YAML files had been checked and parsed normally.

That was 08:33. At 15:58 a different script of mine, which loads the same file with a stricter parser, stopped with:

WS_LAYER0 FAIL: watchlist.yaml YAML 解析失敗：duplicate key: known_positive

(解析失敗 is “failed to parse”.)

What had happened

The entry had a blank line in the middle of it. The loop stopped there. Of the ten lines the entry occupied, it deleted the first eight — the id line, six fields, and the blank line — and left the last two, known_positive: and note:, indented exactly as before.

A blank line does not end a YAML mapping, and neither does a comment. Indentation does. So the two leftover lines were not debris to the parser; they were two more keys of the entry above, which already had a known_positive and a note of its own. PyYAML's safe_load does not reject a mapping with a repeated key. It keeps the last value and says nothing. The YAML 1.2 spec is explicit that “each of the keys is unique”; PyYAML 6.0.3, the version on this machine, does not enforce it.

So after the edit, the file parsed, the removed id appeared nowhere, the number of entries had gone from four to three, and the entry that survived above the gap was carrying the removed entry's evidence and the removed entry's notes in place of its own. The two orphaned lines were 607 and 2,400 characters long, and they sat directly under the removed entry's section comment, which the loop had not touched either. To someone scrolling, they would read as the remains of that section, not as part of the entry above.

Reproducing it

Twenty lines of YAML with the same shape, and the same loop:

$ cat watchlist.yaml
# Conditions an agent checks every morning. One entry per condition.
watches:
  - id: invoice_paid
    predicate: "the vendor invoice shows as paid"
    expiry: "2026-10-31"
    known_positive: "invoice 1041, paid 2026-08-02"
    note: "monthly; re-arm after it fires"

  - id: contract_reply
    predicate: "the other side replies about the contract"
    expiry: "2026-10-31"
    probe: "from:legal@example.org newer_than:14d"

    known_positive: "reply of 2026-07-21, same thread"
    note: "merged two documents into one watch on 2026-09-20"

  - id: release_note
    predicate: "a release note for version 2 is posted"
    expiry: "2026-11-30"
    note: "the posting is the signal, not the release"

$ cat unpin.py
import sys
p, wid = sys.argv[1], sys.argv[2]
L = open(p, encoding="utf-8").read().split("\n")
s = [i for i, l in enumerate(L) if l == "  - id: " + wid]; assert len(s) == 1; s = s[0]
e = s + 1
while L[e].strip() != "": e += 1
del L[s:e+1]  # also drop one trailing blank
open(p, "w", encoding="utf-8").write("\n".join(L))

$ python3 unpin.py watchlist.yaml contract_reply; echo "exit=$?"
exit=0
$ grep -c contract_reply watchlist.yaml
0
$ python3 -c "import yaml; yaml.safe_load(open('watchlist.yaml')); print('yaml ok')"
yaml ok
$ python3 -c "import yaml; d = yaml.safe_load(open('watchlist.yaml')); print(len(d['watches'])); print(d['watches'][0])"
2
{'id': 'invoice_paid', 'predicate': 'the vendor invoice shows as paid', 'expiry': '2026-10-31', 'known_positive': 'reply of 2026-07-21, same thread', 'note': 'merged two documents into one watch on 2026-09-20'}

invoice_paid now says its proof of detectability is a contract reply.

The agent had saved a copy of the real file before editing it, and the repair at 16:00 saved another copy before touching anything. Running unpin.py on the first copy produces a file byte-for-byte identical to the second, so this is the mechanism and not a plausible story about one.

Python's json module, jq, and Ruby's YAML.safe_load (Ruby 2.6) do the same thing with a repeated key: last value wins, no error. I tested those three and no others.

What I got wrong

I read “both files checked, both parse normally” as “the file is right”. The report said something narrower, and it said it accurately.

Both checks asked whether the edit had happened. Neither asked whether anything else had happened. grep -c for the id is a test of absence, and deleting only the first line of the entry is enough to pass it. safe_load is a test of syntax, and the damaged file was syntactically fine. Between them they confirm that something was removed and that what is left is YAML. That is also true of a correct removal, which is why the output looked the way a correct removal looks.

I knew the right check. A month earlier I split this same file into three, and my notes from that day say the split had to be proved by loading the file before and after and showing the two objects were identical; it was. A split is supposed to change nothing, and “nothing changed” is easy to state as a comparison. A removal is supposed to change exactly one thing, and I did not write that one down as a comparison, so nobody ran it.

What caught it, and why that was luck

The script that failed at 15:58 uses a loader I had subclassed to make repeated keys fatal. It caught this because the orphaned lines happened to share field names with their new parent. Change one thing in the reconstruction — let the entry's tail be a field the entry above does not have — and the strict loader has nothing to object to:

$ sed -n 10,11p before2.yaml     # contract_reply's tail; invoice_paid has no probe

    probe: "from:legal@example.org newer_than:14d"
$ cp before2.yaml after2.yaml; python3 unpin.py after2.yaml contract_reply
$ grep -c contract_reply after2.yaml
0
$ python3 -c "import yaml; yaml.safe_load(open('after2.yaml')); print('yaml ok')"
yaml ok
$ python3 -c "import sys; sys.path.insert(0,'checks'); import removal, yaml; d=yaml.load(open('after2.yaml'), Loader=removal.Strict); print('strict ok:', d['watches'][0])"
strict ok: {'id': 'invoice_paid', 'predicate': 'the vendor invoice shows as paid', 'expiry': '2026-10-31', 'note': 'monthly; re-arm after it fires', 'probe': 'from:legal@example.org newer_than:14d'}

That variant is one I constructed; it is not what happened today. In it, the invoice watch has acquired a search query for mail from a legal department, and every parser is satisfied. The only thing that sees it is a comparison against the file as it was before the edit.

Downstream programs are no help either, and correctly so. One of mine reads this file every morning to compute expiry dates. Its source carries this comment: “a broken YAML must never leave yesterday's … JSON for the briefing to mistake as today.” It uses safe_load. I ran it on the real broken file and on the repaired one; the two outputs are identical apart from the timestamp field. It reads ids and dates, and those had not moved.

What generalises

A check that an edit happened is not a check that only the edit happened. After deleting an entry, the claim worth testing is that the result equals the original minus that entry, with every other entry unchanged, parsed by something that treats a repeated key as an error. Absence of the id, a valid parse, and the expected count are all consequences of a correct removal, and all three survive this incorrect one.

The check

checks/removal.py is 108 lines. Given the file before, the file after, and the id that was supposed to go, it answers REMOVED, DAMAGED or UNPARSEABLE. It loads both files with repeated keys made fatal, then compares every surviving entry field by field against the original. Five built-in controls run on every invocation, and if any of them comes out wrong it refuses to classify anything.

$ ./checks/removal.py before.yaml watchlist.yaml contract_reply
control +  UNPARSEABLE  orphaned tail, keys shared with neighbour
control +  DAMAGED      orphaned tail, key new to neighbour
control +  UNPARSEABLE  BEFORE already had a duplicate key
control +  DAMAGED      a top-level key outside the list went missing
control -  REMOVED      clean removal

UNPARSEABLE  watchlist.yaml  (removed 'contract_reply' from before.yaml)
             duplicate key 'known_positive' at lines 6 and 9
exit=1

The constructed variant comes out DAMAGED invoice_paid: gained 'probe'. A correct removal comes out REMOVED with exit 0, and so does the real file as repaired this afternoon, checked against the agent's pre-edit copy.

I broke the script twelve ways. Eleven were caught by the controls, exit 2: making the loader lenient, disabling the repeated-key test, comparing entries by id only, comparing counts only, dropping the “gained a key” branch, forcing either verdict, keeping the wrong entry in the expected list, dropping the top-level comparison, and corrupting either the positive or the negative fixture.

One survived. Forcing the exit status to 0 leaves every control passing: the script still prints UNPARSEABLE, and exits as if it had printed REMOVED. The controls test the classification; what main() does with the classification never passes through them. Anything that reads only the exit status of this check is trusting a line of code that no control covers. I have left it that way and written it down here rather than add a control for the control.

This is a catalogue of cases where a tool reported success, or reported nothing, and I believed it. Each entry gets the date, the commands, and the shape of the error. More will follow.
