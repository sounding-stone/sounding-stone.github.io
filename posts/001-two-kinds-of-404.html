Two kinds of 404

2026‑09‑08   Yu Hsien Fang

One meant the name is free. One meant the registry runs no RDAP service at all. Same field, same value, and I had already printed the wrong answer to my own screen before a control group caught it.

Here is the whole thing, because the useful part is not the conclusion.

The job

I needed to know whether a handful of domain names were available. Five minutes of work. I ran whois:

soundingstone.com  -> Creation Date: 1999-04-27   (excerpted)
soundingstone.dev  -> (no output)
soundingstone.io   -> (no output)
soundings.dev      -> (no output)

The .com has been taken since 1999. Clear enough. The other three returned nothing at all: no record, no error, exit status zero.

Nothing is not an answer. It looks like one, which is the problem. A registry with no WHOIS server produces the same empty output as a name nobody has registered. My client was not lying. It had nothing to say and no way to tell me that.

The second tool, and the actual mistake

So I switched to RDAP, the protocol that replaced WHOIS, and keyed off the HTTP status code:

web.dev              -> 302
github.io            -> 404  (available)
zzq-nope-19f3a7x.dev -> 302
soundingstone.io     -> 404  (available)

That (available) is mine. I wrote the mapping, the mapping was wrong, and it went straight into a report.

github.io serves every GitHub Pages site on the internet. It came back 404. Meanwhile a domain I had invented three seconds earlier came back 302, the same code as web.dev, which very much exists. The status code carried no information about registration at all. It was describing redirects at rdap.org, and I read it as a fact about the world.

Two things saved this, and both were free.

web.dev was in the run as a known‑positive: a name I was certain existed. zzq-nope-19f3a7x.dev was a known‑negative: one I was certain did not. When a known-positive and a known-negative come back identical, the check is dead. Not inconclusive, dead. It cannot separate the two cases it exists to separate, so nothing it says about the unknown cases is worth reading.

The 404 that meant nothing

Following redirects and reading the body fixed the first problem and exposed a second one:

web.dev          -> "ldhName": ...   registered
soundings.dev    -> "ldhName": ...   registered
soundingstone.io -> "errorCode": 404, "title": "No RDAP service in bootstrap for io"
github.io        -> "errorCode": 404, "title": "No RDAP service in bootstrap for io"

.io has no RDAP service. Every .io name on earth returns that 404: registered, unregistered, nonsense. The field is called errorCode, the value is 404, and it sits in the exact position where this name is free also sits. Had I trusted the status code, or grepped only for errorCode, I would have reported every .io name as available with complete confidence.

Available and unmeasurable arrived in the same shape. The only thing separating them was a title string I had no reason to read until a control row forced me to.

There was a fourth case, the one I am least proud of and most glad about. For .org I ran three names, two candidates and one nonsense string, and all three came back 404. That result is unreadable: with no known-positive in the batch I could not tell both free from the whole check is broken. So I added wikipedia.org and mozilla.org, got real records back, and only then trusted the 404s. When the control group is incomplete, the correct move is to not conclude. It costs one more command.

What generalises

Nothing above involved a bug. Every tool did what it documented. Exit codes were zero, HTTP responses arrived, the JSON was valid. All four failures were in the reading, not in the tools. One of them had already been printed as a confident answer before anything caught it; the other three were one incurious grep away from the same fate.

Every check ships with a known-positive and a known-negative in the same batch. Not in a test suite. In the batch, on every run, next to the unknowns you actually care about. If the two controls come back the same, you learned nothing and have to say so. If a control comes back wrong, the check is wrong, and you found out before the answer left the room.

The corollary costs more to accept: a tool's silence is not a negative result, and an error code is not a data point. Empty output, a zero count, a 404 — each has at least two causes, and one of them is always that the pipe never reached the thing you asked about.

checks/availability.sh does the domain case with the controls wired in. It refuses to run the candidates at all if the controls fail to separate. It is 46 lines and it is not the point. The point is the two extra rows in every batch you run.

This is a catalogue of cases where a tool reported success, or reported nothing, and I believed it. Each entry gets the date, the commands, and the shape of the error. More will follow.
