fully inside viewport

2026‑10‑31   Yu Hsien Fang

A mobile page I maintain ends a long list of cards with one button, "Start quiz". On a phone that button sat below the fold, so a change put it in a bar with position: sticky; bottom: 0, which holds it at the bottom edge of the screen while you scroll. The page also has a tab bar fixed to the bottom edge, position: fixed with z-index: 200. The new bar had z-index: 20.

Agents made the change overnight, in four parallel pieces, each with its own end-to-end test, and wrote a smoke script that runs after a deploy on two Playwright device profiles, Pixel 7 and iPhone 13. The run and the merge were mine, so what follows is written as my mistake.

What the smoke reported

Check A was written for the bug being fixed: a button below the fold. Clicking through the cards scrolls the page, so the script scrolls back to the top before it measures, and says why:

  // Clicking 記住了 auto-scrolls the page; measure from the top so a non-sticky
  // button below the fold is caught (sticky one stays pinned to the bottom).
  await page.evaluate(() => window.scrollTo(0, 0));
  await page.waitForTimeout(300);
  const sb = await start.boundingBox();
  check(tag, 'A 開始測驗 fully inside viewport after marking all', !!sb && sb.y >= 0 && sb.y + sb.height <= vh, …);

(記住了 is the "Got it" button on each card.) Then it clicks the button and waits for the first question.

Before trusting check A, the agent ran it against the page as it was before the change. On iPhone 13 it failed, as it should:

"name": "A 開始測驗 fully inside viewport after marking all", "ok": false,
"detail": "cards=60 top=651 bottom=708 vh=664"

Against the change, all 28 checks passed. The iPhone 13 rows:

"name": "A 開始測驗 fully inside viewport after marking all", "ok": true,
"detail": "cards=60 top=595 bottom=652 vh=664"
"name": "A tapping 開始測驗 opens question 1", "ok": true

The change was merged at 00:39 and deployed.

What the screenshot showed

The script also saves a screenshot at that moment, iPhone13-3-all-marked.png. The one from the 28/28 run shows, at the bottom of the screen, the tab bar, and above it a strip of the button's colour. The label isn't there. The numbers say the same thing: the button runs from 595 to 652, the tab bar starts at 616, so 21 of the button's 57 pixels are above it.

After the merge, an agent looking at an iPhone screenshot saw this. The fix, committed at 01:00, lifts the bar's bottom to the tab bar's height plus the safe-area inset, and adds a check that asks the browser which element is at the centre of the button, and requires the button's bottom to be at or above the tab bar's top. Production, with the change deployed, failed it on iPhone 13 and passed everything else, 29 of 30:

"name": "A 開始測驗 not covered by BottomNav (center hit + bottom ≤ nav top)", "ok": false,
"detail": "{\"hitIsButton\":false,\"btnBottom\":652,\"navTop\":616}"

The fix branch passed 30 of 30, with the button's bottom at 604. On Pixel 7 the button was never covered; the taller screen left it above the tab bar.

Why both checks passed

Nothing in the run was wrong about what it measured.

"Inside the viewport" is geometry. A box between 0 and the viewport height is inside the viewport whether or not something is painted over it. Playwright's own assertions say the same. On a 14-line page with a sticky button and a fixed tab bar (below), on the iPhone 13 profile:

  ✓  1 [iPhone 13] › covered.spec.mjs:8:5 › page.html › toBeVisible (271ms)
  ✓  2 [iPhone 13] › covered.spec.mjs:11:5 › page.html › toBeInViewport (170ms)
  ✓  3 [iPhone 13] › covered.spec.mjs:14:5 › page.html › click opens question 1 (365ms)
  ✘  4 [iPhone 13] › covered.spec.mjs:18:5 › page.html › centre of the button is the button (145ms)

toBeInViewport there is called with ratio: 1, the strictest form. It is built on IntersectionObserver, which measures overlap with the viewport, not with other elements. toBeVisible means a non-empty box and no visibility: hidden. Both are documented that way (assertions, "visible").

A click is a robot that scrolls. locator.click() waits for the element, scrolls it into view, checks that the click point would land on it, and retries if not. With DEBUG=pw:api on the same page (timestamps removed, the middle retry cut):

pw:api   element is visible, enabled and stable

pw:api   done scrolling

title: question 1  scrollY: 492

Playwright saw the tab bar on top of the button three times and said so. Then it scrolled the page 492 pixels, to the end, where a sticky element goes back to its place in the flow. The page reserves the tab bar's height as bottom padding, so at the end of the page the button sits above the bar, and the click lands. The test report says "passed". Remove the padding from the toy page and the same click times out (TimeoutError, at the default 30 seconds).

I have not rerun the real page in the covered state. It reserves the tab bar's height the same way, and its tap check has passed on all 10 runs I have results for: the old page where the button was below the fold, the covered one, and the fixed one. On this page that check cannot fail for a layout reason.

What I got wrong

  • I read "inside the viewport" as "on screen". It is a statement about a rectangle. Whether anyone can see the rectangle is a question about what is painted over it, and nothing in the smoke asked.
  • I took a passing click as "a person can tap it". The click answers whether something willing to wait, scroll and retry can eventually click the element. The script's author knew the clicks scroll the page; it says so in the comment above, and resets the scroll before measuring. Then it used a click as the evidence for the tap.
  • The known-positive came from the old bug. Check A had failed on the page before the change, which is why I trusted it. That proved it could see a button below the fold. The change replaced that failure with a different one, a button pinned under the tab bar, which comes from the fix itself. A check proven against the old bug had no way to see it.
  • The evidence was in the output directory. The run that printed 28 of 28 had saved the picture. A count is cheaper to read than a picture, so the count is what I read.

The control

Someone looked at the rendered screenshot. Then the thing the picture showed was turned into a question the browser answers directly: what element is at this point? The check was run against the deployed bad version, where it failed, and against the fix, where it passed, before it went into the smoke. That is the same known-positive discipline as before; this time the known-positive was the new failure, not the old one.

What is still true

  • A hit test answers "would a tap here land on the button", not "can the eye see it". An overlay with pointer-events: none hides the button from the eye and not from elementFromPoint. I ran the check below on that page; it says REACHABLE.
  • Both the smoke's new check and mine measure at one scroll position, the top of the page. The user may be somewhere else.
  • The tap check is still in the smoke and still uses locator.click(). It is harmless now that the hit test runs first, and it still can't fail for a layout reason.
  • The covered version was on production between two deploys in the middle of the night. I don't have the deploy times; the two commits are 20 minutes apart. Going by the toy, which reserves the tab bar's height the same way, scrolling to the end of the page would have shown the whole button; I have not checked that on the real page.

Reproducing it

page-fixed.html differs from page.html in one value: bottom: 48px instead of bottom: 0. page.mouse.click(x, y) at the button's centre does not scroll and does not retry; on the covered page the click goes to the tab bar.

What generalises

  • When the question is whether a person can use something, don't let the test move first. locator.click() scrolls and retries. A raw page.mouse.click() at coordinates, or a hit test at the scroll position the user is at, does neither.
  • Give a fix its own known-positive. A check proven against the old bug proves it sees the old bug. When the fix changes the mechanism (in flow to sticky, static to fixed), write down how the new mechanism fails, build that failure, and make the check fail on it.
  • Read the log of the tool that passed. Playwright printed "intercepts pointer events" three times on a test that passed. Retries that end in success are worth surfacing.
  • If a run saves pictures, a pass includes looking at one. The count and the picture came out of the same run; only one of them showed the problem.

The check

reachable.mjs (69 lines) asks one question about one element: at the top of the page, without scrolling, how much of it would a tap reach? It samples a 5×5 grid over the element's box and asks elementFromPoint at each point. Verdicts are REACHABLE, COVERED (something else is on top of some of it), OFFSCREEN (part of it is outside the viewport, nothing on top) and NO_BOX. Every run first measures six built-in pages with known answers, and refuses to measure yours if any comes back wrong:

$ node reachable.mjs page.html '#start'
control +  COVERED    sticky bar under a fixed nav
control +  COVERED    nav over the bottom fifth, centre clear
control +  OFFSCREEN  plain button below the fold
control +  NO_BOX     button with display:none
control -  REACHABLE  sticky bar above the nav
control -  REACHABLE  label span inside the button

COVERED    #start on iPhone 13  (5/25 points reach it; on top: nav)
exit 1
$ node reachable.mjs page-fixed.html '#start'
…
REACHABLE  #start on iPhone 13  (25/25 points reach it)
exit 0

It exits 0 for REACHABLE, 1 for anything else, 2 if the controls fail, 3 if the page can't be read. "Nav over the bottom fifth" is there for a check that only tests the centre point; "label span" is there for one that counts a hit on the button's own child as a cover.

mutate.mjs breaks it nine ways and runs each mutant on page.html and page-fixed.html:

original: 1 COVERED | 0 REACHABLE
caught    centre point only              2 controls | 2 controls
caught    label span counts as cover     2 controls | 2 controls
caught    scroll to the end first        2 controls | 2 controls
caught    box only, no hit test          2 controls | 2 controls
caught    outside the viewport is fine   2 controls | 2 controls
caught    half reachable is enough       2 controls | 2 controls
caught    zero-size box is measured      2 controls | 2 controls
caught    every verdict exits 0          0 COVERED | 0 REACHABLE
SURVIVED  controls are not enforced      1 COVERED | 0 REACHABLE

9 mutants, 8 caught, 1 survived

"Box only, no hit test" is the smoke's original check A. "Scroll to the end first" is what locator.click() did. The survivor removes the line that refuses to report when a control fails; with every control passing, removing it changes nothing a run can show. It is equivalent here, and it is the one line that has to be read rather than tested.

What it doesn't cover: the pointer-events: none case above, other scroll positions, and anything that happens after a tap lands.
