Everyone came from the homepage

2026‑09‑12   Yu Hsien Fang

One value in a referrer column outnumbered every other value by a wide margin: a bare origin with a trailing slash. I read it as that site's homepage and wrote it into three documents. Nobody's homepage was involved. The field was populated, the counts were right, and the aggregation was correct.

The job

Find out which page on another site was sending people to a site I work on. The analytics tool already had a page-referrer dimension, so this looked like reading one column. The distribution was lopsided in a way that felt like a finding: one value held almost everything, and the rest were deep paths with tiny counts.

I explained that shape before I asked what produced it. That is the whole error, and everything below is the cost of it.

The tail I used as proof

A second, independent measurement of the same question came back with a completely different top entry page. I defended my number, and my defence was the tail: the report did contain rows with full deep paths, so the field clearly was not being truncated.

That argument runs backwards. Those rows were not evidence the field was intact. They were the only rows whose sending site had opted into sending a path at all. I took the residue of the masking as proof that there was no masking.

What the browser actually sends

Two origins on localhost — a page server on :8001, and on :8002 a server that echoes back the Referer header it received. A link from a deep path on the first to the second, clicked in a real browser:

chromium 143.0.7499.4 — link from http://127.0.0.1:8001/deep/path/<page>.html

no policy set                -> Referer: http://127.0.0.1:8001/
no-referrer-when-downgrade   -> Referer: http://127.0.0.1:8001/deep/path/nrwd.html
unsafe-url                   -> Referer: http://127.0.0.1:8001/deep/path/unsafe.html
no-referrer                  -> Referer: None

With no policy set, the browser sent the origin and dropped the path. That is the current default (strict-origin-when-cross-origin), not a misconfiguration — a site does not have to do anything to flatten its own outbound referrers, it has to do something to stop that.

The row that settles it is the one I should have run first:

from ROOT       -> Referer: http://127.0.0.1:8001/
from DEEP PATH  -> Referer: http://127.0.0.1:8001/

Byte-identical. A genuine landing on the root and a withheld path arrive as the same string. Nothing anywhere in the data separates them, which means no amount of care applied to that column would have gotten me to the right answer.

The fourth case is worth its own line. Under no-referrer the header is simply absent — the same thing that arrives when somebody types the URL. A site with a strict policy shows up in the receiver's report as traffic with no source.

What I got wrong

I explained a distribution before asking what generated its values. When one value holds an overwhelming majority and everything else is a long tail of fragments, that majority value is the first place to look for a default, a truncation, or a policy. I treated it as the finding instead of as the thing to check.

I audited a masked field using the field. The surviving full-path rows were a sampling artefact of the masking. I used them as a control group. They cannot be one — they are drawn from exactly the population that behaves differently.

I had the answer available the whole time and ran the command late. One curl -sSI against the referring origin takes a second and returns the policy. I ran it only after being contradicted. There was no Referrer-Policy header and no meta tag, so the browser default applied, so the path was never sent, so my column had always meant “somewhere on that site.”

How much of the web is flattened

I wrote the check below and ran it over thirty sites I had no stake in:

25  ORIGIN-ONLY     (no path can reach you)
 4  NO-REFERRER     (nothing reaches you)
 1  PATH-VISIBLE    (a path-level claim is possible)

One of thirty could support the kind of sentence I had written. Of the twenty-five origin-only sites, most set no policy at all and simply inherit the default.

One wart from that run, because it is the same disease: my first pass read only the response header and reported “no policy set” for two of those sites. Both actually set a policy in a <meta> tag, and they landed in the same bucket anyway. That was luck. Had either used unsafe-url, a header-only check would have been wrong in the direction that matters, and it would have been wrong with exit status zero.

What generalises

Nothing above was a bug. The analytics field was valid and correctly populated, the browser followed its documented default, the counts were accurate, and the conclusion was fabricated. The mistake was reading a field as a record of behaviour when its values were being manufactured by a policy several layers upstream.

Before you read a field, find out what upstream can flatten it, and treat the majority value as the first suspect. A field that is present, valid and well-populated can still be reporting a policy rather than a behaviour. The question is not “is this value correct” — it was correct — but “what range of true states produce this value.”

The corollary is the part that cost me the most: you cannot audit a masked field using that field. The rows that survived unmasked are a sampling artefact, not a control group. The control has to come from outside the data — in this case, the policy the sending origin actually set, which is one request away and which I did not make.

The check

checks/referrer.sh is 67 lines. Given referring origins, it classifies each one PATH-VISIBLE, ORIGIN-ONLY or NO-REFERRER, and it ships a known-positive and a known-negative in every run. If the two controls fail to separate, it refuses to classify the candidates at all.

$ ./checks/referrer.sh en.wikipedia.org news.ycombinator.com github.com \
      www.djangoproject.com techcrunch.com

control +  www.bbc.com                  PATH-VISIBLE  no-referrer-when-downgrade
control -  www.debian.org               NO-REFERRER   no-referrer

en.wikipedia.org             ORIGIN-ONLY   origin-when-cross-origin
news.ycombinator.com         ORIGIN-ONLY   origin
github.com                   ORIGIN-ONLY   strict-origin-when-cross-origin
www.djangoproject.com        NO-REFERRER   same-origin
techcrunch.com               PATH-VISIBLE  no-referrer-when-downgrade

ORIGIN-ONLY and NO-REFERRER origins cannot support any path-level claim.
A bare origin in a referrer report is not a landing on that origin's root.

Broken deliberately, it refuses: pointing the known-positive at an origin-only host exits 2, pointing the known-negative at a path-visible host exits 2, making both controls identical exits 2. An unreachable candidate exits 3.

That last exit code exists because the first version of this script had the bug this entry is about. A host it could not reach fell into the same bucket as a host that reachably sets no policy, and it printed a confident ORIGIN-ONLY verdict for a hostname that does not exist, with exit status zero. The controls did not catch it, because the controls are hardcoded and were perfectly fine. So a caveat on the rule I shipped in 001: a control group proves the method can separate the cases it exists to separate. It does not prove that any particular row is about the thing it names.

This is a catalogue of cases where a tool reported success, or reported nothing, and I believed it. Each entry gets the date, the commands, and the shape of the error. More will follow.
