Entry 001 was about a zero that had two causes. Entry 010 was about a lookup that failed and was folded into “not there”. This one has no failure in it. Every command did what its manual says. The problem is that the command that checked the work was the command that did the work, run a second time.

The job

An agent had spent a day building and shipping a feature for me. Its test runs and reviews had left scratch directories and log files named <prefix>-* in two places: $TMPDIR, which on macOS is a per-user directory under /var/folders, and /tmp. At the end of the day I asked it to clean up.

It took inventory first. This is the command and everything it printed:

$ find /tmp "$TMPDIR" -maxdepth 1 -name '<prefix>-*' -newermt '2026-11-13 00:00' | wc -l; du -shc $(find /tmp "$TMPDIR" -maxdepth 1 -name '<prefix>-*' -newermt '2026-11-13 00:00') 2>/dev/null | tail -1
      42
1.9G	total

It told me there were 42 items from that day, about 1.9 GB of test logs and used test copies. A permission check stopped its first attempt to delete them, so it asked me, and I told it to delete the old temp files as well. It ran:

$ find /tmp "$TMPDIR" -maxdepth 1 -name '<prefix>-*' -exec rm -rf {} +; echo left=$(find /tmp "$TMPDIR" -maxdepth 1 -name '<prefix>-*' | wc -l)
left= 0

(The space after = is wc -l padding the number, split by the shell.) Its report, twelve seconds later (translated):

Every <prefix>-* temp item under /tmp and $TMPDIR is deleted, including the ones from before today. 0 left.

I moved on to the next thing.

What the review found

When a session finishes I have another session close it out: it asks the first one what it did, then a separate agent checks each claim with its own commands. For the temp files that agent ran this (trimmed from a longer command):

$ echo "/tmp:"; ls /tmp | grep -c <prefix>; echo "TMPDIR:"; ls "$TMPDIR" 2>/dev/null | grep -c <prefix>
/tmp:
53
TMPDIR:
0

Fifty-three entries. The most recently modified ones were last touched at 10:08 that morning, eight hours before the inventory ran. The cleanup session confirmed it and showed why:

$ ls -ld /tmp
lrwxr-xr-x@ 1 root  wheel  11 Oct 23 07:10 /tmp -> private/tmp

Why nothing was wrong

On macOS, /tmp is a symbolic link to /private/tmp. find has three modes for symbolic links, and the default does not follow them, including one you name as a starting point. POSIX puts it this way: “If neither the -H nor the -L option is specified, then the file information and type for symbolic links encountered as a path operand on the command line or encountered during the traversal of a file hierarchy shall be that of the link itself.” The macOS man page lists -P, “the file information and file type … returned for each symbolic link to be those of the link itself”, and adds: “This is the default.”

So find /tmp looks at one thing, the link, whose name is tmp. It does not match <prefix>-*, and a link is not a directory, so there is nothing to descend into. On this machine today, read-only:

$ find /tmp -maxdepth 1
/tmp
$ find /tmp -maxdepth 1 | wc -l
       1
$ find /tmp/ -maxdepth 1 | wc -l
     333
$ find -H /tmp -maxdepth 1 | wc -l
     333

$TMPDIR is a real directory, so find did go into that one. The 42 and the 1.9 GB were $TMPDIR alone. The delete removed what was in $TMPDIR and nothing in /tmp. The recount looked at the same two places the same way and found nothing in either. Nothing printed an error, rm was never handed a /tmp path, and wc counted the lines it was given. Each number was correct about what had been looked at.

To be sure the story holds without my reading it into the transcript, I rebuilt it in a scratch directory, with a symbolic link named tmp pointing at a directory holding 53 entries and a second directory standing in for $TMPDIR with 42, and ran the agent’s commands unchanged except for those two paths and the prefix (repro.zsh):

$ find tmp "$T" -maxdepth 1 -name 'proj-*' | wc -l
      42
$ find tmp "$T" -maxdepth 1 -name 'proj-*' -exec rm -rf {} +; echo left=$(find tmp "$T" -maxdepth 1 -name 'proj-*' | wc -l)
left= 0
$ ls -d tmp/proj-* | wc -l
      53

What I got wrong

I accepted a deletion as verified because the selector that chose what to delete then reported nothing left to delete. Those two runs of find were never going to disagree. Anything the first one could not see, the second could not see either. A check that shares the action’s way of looking can only confirm the action; it cannot catch it.

The inventory had the same problem, and that one reached me. “42 items, about 1.9 GB” was the scope I was agreeing to clear, and it came from the same lookup. Nothing in that number could have told me it was missing a directory.

I had a rule for the opposite case. When I compare a measurement before and after a fix, I use the same instrument both times, because a different instrument makes the comparison meaningless. That rule is right, and I had stretched it to cover this one, where it is wrong. Confirming that an action took effect is a different question from comparing two states, and it needs a different instrument.

How the review caught it

It did not know about the symlink. It counted with ls /tmp, a different program, and ls follows a symbolic link named as an argument when it lists a directory. That was enough for the two answers to disagree, 0 against 53.

ls is not independent by nature. ls -l /tmp or ls -d /tmp shows the link itself and would have counted nothing. The review was right because it took a different path to the same files, and that path happened to resolve the link.

The rule I installed

Confirm a deletion with a lookup that resolves paths differently from the one that chose the targets. If find selected them, count with the shell’s glob (ls -d /tmp/<prefix>-*), or list the resolved directory (realpath, then read it). Better still, name one target you know was there and check that it is gone.

Calibrate the selector before you act, with a planted positive. Create one <prefix>-canary where the files live and make sure the inventory counts it. A find /tmp that cannot see the canary would have printed 42 instead of 43, and that would have stopped the run.

For find in particular: start from /tmp/ with the slash, or pass -H. Either makes the starting point the directory rather than the link.

Keep both rules. Before-and-after comparisons use the same instrument. “Did my action take effect” uses a different one.

Run it

checks/011/cleanup_check.py takes a cleanup command and a count command as templates. {root} is the directory, {pat} is the pattern quoted for find -name, {glob} is the same pattern unquoted for the shell. It builds two fixtures in a temp directory: a real directory, and a symbolic link to a directory. Each holds four targets, one of them with a space in its name, and two decoys that must survive. It knows what is left by listing os.path.realpath(root) with os.listdir and fnmatch, so its answer does not come from find or from the shell. It runs five controls first and refuses to judge the target if they do not come out as expected.

On the shape the agent used (with rmdir in place of rm -rf, since the fixtures are empty directories):

$ python3 cleanup_check.py "find {root} -maxdepth 1 -name {pat} -exec rmdir {} +" "find {root} -maxdepth 1 -name {pat} | wc -l"
control OK    find deletes, same find counts: FALSE-CLEAN
control OK    find deletes, ls counts: NOT-CLEAN
control OK    nothing deleted, count is echo 0: FALSE-CLEAN
control OK    glob rmdir, ls counts: ok
control OK    find with trailing slash, same find counts: ok
FALSE-CLEAN
  ok  real directory     ok
  BAD root is a symlink  FALSE-CLEAN   count said 0, 4 still there
$ echo $?
1

FALSE-CLEAN means the count said 0 while targets were still there, exit 1. NOT-CLEAN means the cleanup failed but the count told the truth, exit 4, which is also what you get when a decoy is removed. Starting find from {root}/ and counting with ls prints OK and exits 0. It takes about 0.1 seconds.

The controls earned their place on the first run. My first version quoted the pattern everywhere, so ls -d '<root>/proj-*' looked for a file literally named proj-*, found none, printed nothing to the pipe, and wc -l said 0:

control WRONG find deletes, ls counts: FALSE-CLEAN
control WRONG glob rmdir, ls counts: FALSE-CLEAN
controls did not separate; not judging the target

The script that looks for a count that reads 0 because nothing looked had a count that read 0 because nothing looked. It stopped itself because two controls disagreed with what they should have been.

I broke it eleven ways with checks/011/mutate.py and ran each version against nine cleanup and count pairs with known answers. Eight changed at least one answer. Three did not: switching off the control enforcement, removing the fixture self-check, and returning exit 1 instead of 3 on a fixture error. On a healthy run those three behave exactly like the original, so these tests cannot tell them apart. I also tried the mistake this entry is about: an oracle that uses find to see what is left, with the self-check removed so nothing else stops it. The first control then comes out ok instead of FALSE-CLEAN, and the script exits 2 without judging anything.

I ran all of this on macOS 27.2.1 with Python 3.14.6 and 3.9.6 and the system find. Tested on macOS only. The fixture makes its own symbolic link, so the check does not depend on how a machine sets up its /tmp. For other implementations of find I claim only what the POSIX text quoted above says; I have not run the script against GNU findutils.

This is a catalogue of cases where a tool reported success, or reported nothing, and I believed it. Each entry gets the date, the commands, and the shape of the error. More will follow.
