That’s all of them

2026‑09‑19   Yu Hsien Fang

Last entry was about a referrer column whose majority value was manufactured by a policy upstream. It had a loose end at the bottom, which I moved here because it turned out to be the more expensive half:

Because the masking pushes nearly everything into a single value, the informative rows are all rare, which means they all sit at the bottom of a report sorted by count. The query behind my original table had a row limit on it. The rows that could have answered the question were below the cut, and they were below the cut for the same reason they were informative.

What I did not notice when I wrote that is that a trimmed result and a complete one can be identical on screen — identical to the byte, as it turns out — and that the only thing standing between them is a number I habitually skip.

Two queries, five rows each

GitHub's search API takes a per_page parameter, and reports the size of the whole match set in total_count. Two queries, both at per_page=5, eight seconds apart:

q=stars:>390000   total_count=6   len(items)=5
q=stars:>395000   total_count=5   len(items)=5

Both returned five rows, and not just the same five repositories in the same order with the same star counts: the two items arrays are the same 34,246 bytes, sha256 638ac4994d0fc41f…. The first is missing a repository. The second is complete. I know the missing one is openclaw/openclaw at 390,033 stars only because I went and asked for page two.

Both responses are correct and both fields are documented; nothing here is a bug. But nothing in the rows tells you which case you are in. Three queries with genuinely different answer sizes, all at per_page=5:

language:rust stars:>10000    total_count=251   items: 32,524 bytes, sha256 414046569362453f
language:rust stars:>60000    total_count=23    items: 32,524 bytes, sha256 414046569362453f
language:rust stars:>100000   total_count=8     items: 32,524 bytes, sha256 414046569362453f

Three different true totals, one identical page. The rows cannot tell you the total, and no amount of care applied to the rows will change that. Two commands, if you want to watch it happen:

for s in 390000 395000; do
  curl -sS -H 'Accept: application/vnd.github+json' \
    "https://api.github.com/search/repositories?q=stars:%3E$s&per_page=5" \
  | python3 -c "import json,sys; d=json.load(sys.stdin); print(d['total_count'], len(d['items']))"
  sleep 8   # unauthenticated search is limited to ten requests per minute
done
# ->  6 5
#     5 5

What I got wrong

I wrote an exhaustive sentence about a result I had bounded myself. Words like all, only and the rest are claim a denominator, and per_page=5 guarantees I never saw one. Both facts sat in the same shell command.

head makes me careful and limit does not. Piping into head -20 looks like formatting, so it feels like throwing data away. per_page=5 and LIMIT 5 look like part of the question being asked. They do the same thing, and the one that reads as a query parameter is the one I stop watching.

Re-reading cannot catch this, and I re-read. My double-check re-ran the same command. A second look verifies that I read the output correctly, and the output was incomplete identically both times.

The same shape in something I wrote myself

I keep date labels in notes, in the form 2026-09-19 (Sat). The weekday is the part I get wrong, because it is derived rather than copied, so I wrote a 26-line checker for it. What follows is a rebuild of that checker in an English-locale form so it runs anywhere; every output in this section is from the rebuild, not from the original incident. Four labels, one wrong on purpose:

$ python3 datecheck.py notes_md.md 2026
WRONG: 9/21 (Wed) -> Mon, not Wed
1/4 label(s) WRONG.
exit=1

Then the same four labels, with the same one still wrong, written the way I actually write dates:

$ python3 datecheck.py notes_iso.md 2026
0 label(s) checked, all correct.
exit=0

The pattern was (\d{1,2})/(\d{1,2})\s*\((\w{3})\) and the second file says 2026-09-21 (Wed). So the checker examined nothing, found no mismatches among the nothing it examined, and said so accurately. 0 label(s) checked and all correct are both true, exit zero is correct, and the screen says the file is fine.

A verifier cannot count what it failed to recognise, which means the denominator it prints is the size of its own reach and not the size of the job. Printing more numbers does not by itself fix that.

The fix is a third state. Widen the pattern, report the count, and refuse to pass when the count is zero — the verdict half of the diff:

+    if total == 0 and allow_empty:
+        print("0 label(s) found - nothing to check (--allow-empty).")
+        return 0
+    if total == 0:
+        print("NOTHING CHECKED - 0 date label(s) found. This is NOT a pass.")
+        print("  Either the text has no label, or the label is in a form")
+        print("  this checker does not recognise. Pass --allow-empty to accept.")
+        return 2
     if bad:
         print(f"{bad}/{total} label(s) WRONG.")
         return 1
-    print(f"{total} label(s) checked, all correct.")
+    print(f"{total} label(s) checked, 0 wrong.")
     return 0

That third exit code is not free. The hook that consumed this checker treated any nonzero status as “wrong label”, so two files with no dates in them went from passing to blocked without my touching the hook at all. Changing a verdict is a data change; changing the vocabulary of verdicts is an interface change. That is a separate entry.

What generalises

A verdict is only as good as the denominator it was computed over, and most tools do not print the denominator. len(rows) == page_size is the exact case where “I fetched a slice” and “that is all of it” produce identical output. checked == 0 is the exact case where “everything passed” and “I examined nothing” produce identical output. In both, the number that separates them exists somewhere, and in both I had not read it.

So: never let a denominator of zero, or of exactly your own limit, exit as a pass. Report it as unmeasured, and make the caller handle that as a third state.

The check

checks/exhaustive.py is 122 lines. Given a paginated URL with a {n} page-size slot, it classifies each endpoint COMPLETE, TRUNCATED or UNMEASURABLE. A declared total is the only thing that can earn COMPLETE; where none is declared it probes one row past the page size, which can prove truncation but never completeness. It runs a known-positive and a known-negative fixture on every invocation and refuses to classify anything if the two fail to separate.

$ ./checks/exhaustive.py items total_count 5 \
    'https://api.github.com/search/repositories?q=stars:%3E390000&per_page={n}' \
    'https://api.github.com/search/repositories?q=stars:%3E395000&per_page={n}'

control +  control-truncated.json   TRUNCATED     fixture, declared total 4210, returned 5
control -  control-complete.json    COMPLETE      fixture, declared total 3, returned 3

TRUNCATED     http 200, declared total 6, returned 5
COMPLETE      http 200, declared total 5, returned 5

TRUNCATED or UNMEASURABLE cannot support 'all', 'only' or 'the rest are'.
exit=1

Eleven deliberate breakages, all caught. Corrupt either control, in any of six ways, and it exits 2 without classifying anything. Hand it a broken candidate — an HTTP error, a rows key that is not a list, a real rate-limit body, a page size clamped at or below what you asked for — and it exits 3.

The rate-limit case is not hypothetical. I hit the unauthenticated search limit while measuring this entry — ten requests per minute — and the 403 body is valid JSON with a message field, no items and no total_count. Had I written the version I would normally write:

t = d.get('total_count', 0); n = len(d.get('items', []))
print(f'total_count={t}  len(items)={n}  ' + ('TRUNCATED' if n<t else 'COMPLETE'))

→  total_count=0  len(items)=0  COMPLETE
   exit status: 0

A defensive default turns a rate-limit error into a confident report that there is nothing there. Same disease one layer down: 0 as a fallback is a denominator I made up.

The script also shipped with the bug this entry is about, and the controls did not catch it. Where no total is declared, the fallback is to ask for n+1 rows and see whether an extra one arrives. GitHub clamps per_page to 100, so at page size 100 asking for 101 returns 100 again — and the first version read that as “there are exactly 100”: COMPLETE, exit 0, for a query whose declared total_count was 251. The probe has its own invisible ceiling, and my controls are fixtures, which never clamp.

It shipped that way in two branches, not one. The other reads “fewer rows came back than I asked for, so that must be all of them” as exhaustion, and printed COMPLETE, exit 0, for that same 251-row query at page size 500. Both are UNMEASURABLE now.

The repair is a demotion rather than a fix:

UNMEASURABLE  http 200, returned 100; page size 101 also returned 100
              - exactly-100 and page-size-clamped-at-100 are indistinguishable

If asking for n+1 returns n again, the answer is UNMEASURABLE, because “there are exactly n” and “this endpoint caps page size at n” cannot be told apart from outside. Which means the n+1 probe can only ever prove truncation, never completeness. Only a declared total can do that, and where an endpoint declares no total, an exhaustive claim about it is not available to you at any page size. That is a second caveat on the control-group rule from 001: a fixture cannot exhibit a limit that only the live endpoint imposes.

This is a catalogue of cases where a tool reported success, or reported nothing, and I believed it. Each entry gets the date, the commands, and the shape of the error. More will follow.
