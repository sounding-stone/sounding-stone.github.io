message equality is false

2026‑11‑08   Yu Hsien Fang

I run a scheduled job on Cloud Functions. Each run works through a batch of items. For every item that fails, it logs one ERROR line; at the end of the run it logs one INFO summary with counts. Alert policies in Cloud Monitoring match those lines and email me. The policies live in code, and CI applies them after each deploy.

One policy has a clause for the per-item line. The service that runs the job also logs ERRORs that belong to a different alert, so for that service the clause counts only the per-item line, which it recognises by its text:

severity>=ERROR AND (resource.labels.service_name!="<worker>" OR jsonPayload.message="[<job>] Scheduled <item> failed — continuing run")

The logging call and the job's tests are older. The clause and the policy test came from an agent run on October 1, a coding agent and then rounds of review by a second one, and I merged it. The run and the merge were mine, so what follows is written as my mistake.

Two suites, both green

The policy suite checks the filter it generates:

  assert.match(summary, /Scheduled <item> failed/);

The job's suite runs a batch where two items fail and checks what the job logged:

    const error = vi.spyOn(logger, "error").mockImplementation(() => undefined);
    …
    const failures = error.mock.calls.filter(([message]) =>
      message === "[<job>] Scheduled <item> failed — continuing run");

Rerun today at the October 1 commit, the policy suite:

ℹ tests 12
ℹ pass 12
ℹ fail 0

and the job's suite:

 Test Files  1 passed (1)
      Tests  16 passed (16)

The two suites agree with each other: the string in the filter is the string in the code. Neither looks at what reaches Cloud Logging. The second one replaces logger.error with a function that returns undefined, so whatever the real one does with its arguments never happens in the test.

What the logger writes

The SDK's type declaration for logger.error:

 * Writes an `ERROR` severity log. If the last argument provided is a plain object,
 * it is added to the `jsonPayload` in the Cloud Logging entry.
 * @param args - Arguments, concatenated into the log message with space separators.

The implementation, in lib/logger/index.js (6.6.0, line 142):

    let message = (0, util_1.format)(...args);
    if (severity === "ERROR" && !args.find((arg) => arg instanceof Error)) {
        message = new Error(message).stack || message;
    }

At ERROR, when none of the arguments is an Error, the message is replaced by the stack of a new Error built from it: Error: in front, stack frames after. When one of the arguments is an Error, util.format prints that error's stack into the message anyway. Either way, the message of an ERROR line is not the string the code passed. The latest release, 7.4.0, has the same four lines. I haven't found this behaviour in Firebase's logging guide; it is in the source.

Cloud Logging's query language says "The = operator is exact equality." So jsonPayload.message="[<job>] Scheduled <item> failed — continuing run" cannot match a value that begins with Error: . And if the field ended up anywhere other than jsonPayload.message, the same page covers that too: "Using a missing field won't display an error, but all comparisons using missing fields fail silently."

The same shape, in 14 lines anyone can install (below):

✔ the job hands the logger the message the filter expects (0.455666ms)
✔ the filter matches that message exactly (0.062875ms)
✖ the entry the real logger writes has that message (28.7765ms)

It had been printed

CI applied the October 1 version of the policy about 40 minutes after the merge. The deploy for the merge itself stopped at a failing end-to-end test; the next deploy on the main branch applied all six policies and read them back. Before the apply step, that deploy runs the job's tests, and one of them, written for a different behaviour, doesn't mock the logger. Four and a half minutes before the policy was applied, the deploy log has, three times:

"severity":"ERROR","message":"Error: [<job>] Scheduled <item> failed — continuing run\n    at entryFromArgs (…/firebase-functions/lib/logger/index.js:144:19)…

It went by as stderr from a passing test, in a step that passed.

Who noticed

On November 4 a different change touched the same policy. A fresh reviewer session was told to judge only against the acceptance list, not against the developer's notes. It ran the job with the real SDK logger in a subprocess, parsed the JSON the logger printed, and reported (my translation):

Reproduced with the real logger: the log with failedAttempts=2 is ERROR, but message equality is false; the ingestion policy excludes it by its category. So this single log matches zero policies.

The fix matches the per-item line on fields the job sets itself (a fixed failureCategory and the severity) instead of the message. Its test starts a child process with the real logger, parses what it prints, and evaluates the generated filter against that, with a small evaluator for the operators these policies use. That evaluator is not Cloud Logging, and the test says so.

What it cost

The end-of-run summary had its own clause, matching jsonPayload.message="[<job>] Scheduled run done" with a failure count above zero. That line is INFO, the logger leaves INFO messages alone, and that clause can match. So a run with failures should still have emailed me, from the summary. What was dead was the per-item clause: the one that carries each item's error code, and the only one that fires if a run dies before it writes its summary. CI applied it on the evening of October 1, and it stayed until the fix was applied on the afternoon of November 4. I haven't checked whether any run in that window died before its summary.

What I got wrong

  • I read two green suites as one check. One proved the filter contains a string. The other proved the code passes that string to a function. The link between them, that the function writes the string, was in neither.
  • A mocked logger is a statement about my code, not about my logs. The mock answered "what did the job ask for". The alert depends on "what got written", and the mock is exactly the part that was removed.
  • I took silence as health. A clause that matches nothing looks the same as a clause on a system that isn't failing. For almost five weeks that clause sent nothing, and that was consistent with both.

The control

Someone ran the real logger and read what it wrote. That is the known-positive for an alert: one real event, through the real logging path, and the alert's condition evaluated against the entry that came out, not against the argument that went in.

The other alert I added that day

The same change added a metric-absence policy: warn if no "run complete" line arrives for 23.5 hours, counted by a log-based metric created that afternoon. CI applied it alongside seven updated policies and read every policy back. From the deploy log, names replaced:

"policy":"<job> completion absent for 23.5h","action":"created"
"verifiedPolicies":8,"ownerChannels":1

A readback proves the stored policy equals the definition. It doesn't prove the policy can fire. Two lines from Google's documentation:

  • Metric-absence: "For the condition to be met, the monitored subsystem must write at least one data point after you create or modify the alerting policy."
  • Log-based metrics: "The data for a user-defined log-based metric comes only from log entries received after the metric is created."

So on the day it was applied, with verifiedPolicies:8, that policy could not have fired. It can from the first run that writes a point after it. I haven't yet checked that the point arrived.

What generalises

  • Alert on fields you set, not on fields a library formats. A message string passes through code you didn't write. A field with a fixed value you put there yourself usually doesn't.
  • Test an alert against the real logger's output. Run the logging call for real, capture what it prints, and evaluate the condition against that. A test with a mocked logger checks what you passed.
  • After creating or changing an absence alert, check the metric has a point. Until it does, the alert is armed and cannot fire.
  • "No incidents" is also what a dead alert shows. It only means something once the alert has fired at least once on purpose.

Reproducing it

I ran this on Node 24. Everything is in checks/009/; its package.json pins firebase-functions 7.4.0.

npm i --legacy-peer-deps
node --test pair.test.mjs        # 2 pass, 1 fail; same with firebase-functions@6.6.0

--legacy-peer-deps skips installing firebase-admin; the logger doesn't need it, as long as you require firebase-functions/logger rather than the package root. The logger writes ERROR lines to stderr and INFO lines to stdout, so capture both. job.cjs is the job, policy.cjs the filter, pair.test.mjs the two green tests and the red one.

The check

written.mjs (64 lines) asks one question: for a logging call you describe, does the entry the real logger writes still carry the values you passed, field by field? It runs the call in a child process with the firebase-functions installed next to it and compares. Verdicts per field are SAME, CHANGED and MISSING. Every run first checks seven calls with known answers and refuses to check yours if any comes back wrong:

$ node written.mjs error "nightly job failed" '{"category":"nightly"}' message category
control +  CHANGED  message   error("x")
control +  CHANGED  message   error("x", err)
control +  MISSING  category  error("x"), no fields
control -  SAME     message   info("x")
control -  SAME     message   warn("x")
control -  SAME     message   info("two\nlines")
control -  SAME     category  error("x", {category})

CHANGED  message   passed "nightly job failed"  written "Error: nightly job failed\n    at entryFromA..."
SAME     category  passed "nightly"
exit 1

It exits 0 if every field you named is SAME, 1 otherwise, 2 if the controls fail, 3 on bad input or when the logger can't be loaded. Run with only category named, the same call exits 0: that is the field to alert on.

mutate.mjs breaks it eight ways and runs each mutant on two calls, one naming message and one naming category:

original: 1 CHANGED | 0 SAME
caught    compare the argument with itself     2 controls | 2 controls
caught    build the entry from the arguments   2 controls | 2 controls
caught    substring match (the : operator)     2 controls | 2 controls
caught    read stdout only                     2 controls | 2 controls
caught    first line of the message only       2 controls | 2 controls
caught    a missing field counts as same       2 controls | 2 controls
caught    every verdict exits 0                0 CHANGED | 0 SAME
SURVIVED  controls are not enforced            1 CHANGED | 0 SAME

8 mutants, 7 caught, 1 survived

"Build the entry from the arguments" is what a mocked logger does. "Substring match" is Logging's : operator, which would have matched the rewritten message; switching the clause to : would have hidden the problem rather than fixed it. The survivor removes the line that refuses to report when a control fails; with every control passing, removing it changes nothing a run can show. It is the one line that has to be read rather than tested.

What it doesn't cover: what Cloud Logging stores, what a filter matches there, and loggers other than this one. For those, the rule above still applies: one real event, the real path, the real entry.

This is a catalogue of cases where a tool reported success, or reported nothing, and I believed it. Each entry gets the date, the commands, and the shape of the error. More will follow.
