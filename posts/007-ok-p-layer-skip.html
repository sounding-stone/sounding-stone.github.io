OK — P layer SKIP

2026‑10‑16   Yu Hsien Fang

My calendar tool writes a to-do list every morning. Some items on it are reminders to answer an invitation I've marked tentative; others are things I need to prepare before a meeting. A downstream tool hides the first kind and must never hide the second. So the reminders that should be hidden carry a marker, (📅tentative), and a lint checks the list after it is written. One layer of that lint, layer P, fails the run when a marked line also contains a preparation word ("before the meeting", "prepare", "read") — that line is something to do, and the marker would hide it.

Layer P reads its word list from a YAML config that two tools share. The lint loads it without a YAML library, with one regular expression over one line:

VETO_LINE = re.compile(r"^\s*prep_veto_terms:\s*\[(.*)\]\s*$")

and its docstring says what happens when that fails (translated): "can't read it → print SKIP, the layer doesn't run."

Agents wrote the lint, its regex, the SKIP branch and the test fixtures, during an overnight run I had set going before bed: a coding round and a review round, repeated. I chose what the run should build and how it would be reviewed; I had not read that regex or the SKIP branch. The run and the agents were mine, so what follows is written as my mistake.

What the round reported

At 01:36 the coding agent committed round "4b". Among other changes, it added five English preparation words to the list and left a note on the same line:

    prep_veto_terms: ['會前', '先看', … , 'Prepare', 'Prep', 'Draft', 'Review', 'Read']  # r4b：英文準備詞——擋來源人名槽與事件名

(The comment says, translated: "r4b: English prep words — block the source-name slot and event names.") The round's write-up listed this effect (translated): "Side effect: lint layer P and the event-name veto also pick up these 5 words (only in the keep / go-red direction)." Its verification line:

pytest 381 passed；lint 30 tests OK（3.9）

All of that was accurate about what had been run. The 30 lint tests passed. None of them read the config file the lint uses in production. The ones for layer P write their own config into a temp directory:

SOURCES = """sources:
  <tool>:
    <marker_key>: "(📅tentative)"  # c
    prep_veto_terms: ['會前', '先看', … ]
"""

Twelve terms, no comment on that line. (There is a comment one line up, on a key the regex never looks at.) One test, test_loader_parses_flow_list, checks that this fixture loads 12 terms. Another, test_no_sources_skips_p_layer, checks that with no config at all the lint exits 0. The suite asserts the skip.

My agent re-ran those 30 tests today, at the version the reviewer was handed. They pass. Of the 38 lines they print, 15 contain P 層 SKIP, because the tests for other layers don't bother to supply the word list. On a green run of this suite, "P layer SKIP" is what the background looks like.

What the reviewer did

The next round went to a reviewer agent that had not seen the development. It did not rerun the tests and stop. It built a to-do line that layer P must fail — a tentative marker on a line that says "prepare the slides before the meeting":

暫定，會前準備投影片 (📅tentative)

and ran the real lint against the real config file:

rc=0
rsvp-lint: OK … P 層 SKIP（<config>.yaml 無 prep_veto_terms）

Then it changed one thing. It made a copy of the config with only the trailing comment removed and ran the same input:

rc=1、P 層啟用：否決詞 17 個、P-prep 命中

(translated: "rc=1, layer P on: 17 veto terms, P-prep hit".) Its report listed this as the third of three blocking issues: the comment had switched the layer off, and "the existing lint tests still use the comment-free 12-term fixture, so 30 tests all green did not catch this regression."

The next round replaced the regex with a small loader that tolerates trailing comments, multi-line lists and block lists, and added tests that read the real config file and compare the lint's reading of it with PyYAML's. The round's commit is timestamped 01:48. By the commit clock, layer P had been off for about twelve minutes, in the middle of the night. The first scheduled run that uses this lint is at 07:00. No real to-do list went through it while it was off.

What I got wrong

  • I let "couldn't read the rules" mean "no rules". The loader has three ways to come back empty: the file is missing, no line matches the pattern, or the line is there in a shape the pattern doesn't accept. All three print SKIP and exit 0. Only the first two are about the config. The third is about the loader.
  • The reason on the SKIP line was the loader's view, printed as a fact about the file. "The file has no prep_veto_terms" means "no line matched my regex". The file had the key and 17 terms.
  • I counted "30 tests OK" as evidence about the config. Tests that write their own config can't see a change to the real one. Here the change was a comment, which is the edit an agent is most likely to make to a config, because it annotates what it touched.
  • The pipeline reads exit codes. The lint's wrapper writes FAIL — when the exit code is not zero, and the morning check looks for FAIL —. The word SKIP was on the screen, in the same line as OK, and nothing downstream reads that far.
  • The write-up said the new words would reach the lint. It said so about the edit that stopped the lint from reading them. That sentence was a prediction, written next to verified results, and I would have read it as one of them.

The control

The reviewer's isolation step is the part I want to keep. It ran a known-positive through the live config, saw nothing fire, and then varied exactly one thing to show which thing mattered. The known-positive answers "does this layer fire at all"; the one-variable copy answers "why not".

There is a small footnote to it. During the fix round the reviewer's script was run again. It builds the comment-free copy by splitting the line on the comment's exact text, # r4b：. The fix round had reworded that comment, so the split found nothing, and the "comment-free" copy came out byte-identical to the real file. Both rows printed SKIP:

"actual_config":        "rc": 0, … P 層 SKIP（<config>.yaml 無 prep_veto_terms）
"comment_removed_copy": "rc": 0, … P 層 SKIP（sources-without-inline-comment.yaml 無 prep_veto_terms）

Nobody was misled; the fixer checked the new lint against the real file separately and got rc=1 and 40 terms. But in that rerun the control and the thing under test were the same file, and the only sign of it was that they agreed.

What is still true

The fix closed this shape. It did not change what the lint does when it can't read the list. My agent ran today's lint against two configs it still can't read. Both are things a person or an agent might write. The first is valid YAML (PyYAML reads two terms from it):

    prep_veto_terms: [會前, 準備]
rsvp-lint: OK — <list>.md · SKIP（快照不存在：none.yaml） · P 層 SKIP（unquoted.yaml 無 prep_veto_terms）
rc=0

The second misspells the key (prep_veto_term:); same output, rc=0. The parity test added in the fix would catch either one in the real file, the next time someone runs the tests. The morning run doesn't run the tests.

Reproducing it

Python 3, no packages. toy_lint.py (below, 38 lines) has one layer and the same single-line loader. Two configs that differ by a comment:

$ cat a.yaml
rules:
  prep_terms: ['before', 'prepare']
$ cat b.yaml
rules:
  prep_terms: ['before', 'prepare', 'Read']  # added Read
$ python3 toy_lint.py todo.md a.yaml
lint: FAIL - 1 line(s) · P on: 2 terms
   [P-prep] line 1: prep word 'prepare' on a tentative line
exit 1
$ python3 toy_lint.py todo.md b.yaml
lint: OK · P SKIP (b.yaml has no prep_terms)
exit 0

PyYAML on b.yaml returns {'rules': {'prep_terms': ['before', 'prepare', 'Read']}}.

What generalises

  • A checker that can't load its rules should exit non-zero. Skipping a layer is a decision about the config, and only the config should be able to make it: an explicit enabled: false, not a regex that didn't match. Keep "absent" and "unreadable" as two different messages.
  • Test against the file in use. A fixture tests the code. To test the code with the config, read the real config in at least one test, and compare your loader's reading with a real parser's.
  • Prove each layer fires, every run, with the live config. Put one line you know is wrong through the real command and require the specific failure. If you can only afford one check, this is the one; it doesn't care why the layer went quiet.
  • Read the whole line, not the exit code. If a tool prints SKIP, the summary should say how many layers ran, and whatever reads the summary should require all of them.
  • Check that your control differs from the subject. A control built by string surgery can quietly stop changing anything.

The check

skip_canary.py (40 lines) runs a lint command twice against the config you pass — meant to be the live one. The known-positive must exit exactly 1 and print the tag of the layer under test; the known-negative must exit 0. Anything else is a rejection, and both outputs are printed, so a skip line can't hide behind a summary.

Against the real round-4b lint and its real config line (reconstructed from the round's diff):

positive rc=0
  rsvp-lint: OK — <list>.md · SKIP（快照不存在：none.yaml） · P 層 SKIP（with_comment.yaml 無 prep_veto_terms）
negative rc=0
  rsvp-lint: OK — <list>.md · SKIP（快照不存在：none.yaml） · P 層 SKIP（with_comment.yaml 無 prep_veto_terms）
REJECT: positive exited 0, not 1: the layer did not fire

The same lint with the comment removed is accepted (P 層啟用：否決詞 17 個, [P-prep] line 4). Today's lint is accepted on that config and on the live file (40 terms), and rejected on the unquoted list above.

controls.py runs the canary against 11 cases with known answers: the toy lint with a good config (accept), a trailing comment, an unquoted list, a block list, a misspelled key and a missing file (all reject), and five broken lints — always red, warn-only (prints the finding, exits 0), finds-then-errors (exit 2), crashes, and a lint where a different layer fires (all reject). 11/11. mutate.py breaks the canary six ways: drop the positive check, count any non-zero exit as a fire, drop the layer-tag check, drop the negative check, ignore its own problems, and test a built-in copy of the config instead of the one passed in. Each mutant makes at least one control fail. 6/6.

What it doesn't cover: it runs when you run it. Wired into the morning pipeline, it would have turned the 07:00 run red if the fix had not landed first; run by hand, it catches nothing you didn't think to run it on.

This is a catalogue of cases where a tool reported success, or reported nothing, and I believed it. Each entry gets the date, the commands, and the shape of the error. More will follow.
