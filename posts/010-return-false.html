Entry 001 ended on this sentence: “Empty output, a zero count, a 404 — each has at least two causes.” This entry is the boolean version of it, inside a guard. In a guard, which of the two causes wins decides whether something gets written.

The job

I keep my notes and tasks in one folder, and eight programs write to it: scheduled jobs, a journal script, a git commit hook, and the task CLI from entry 006, among others. I wanted to move the folder to another machine, and for that I needed a switch that stops every write while I copy. The switch is a flag file outside the folder, ~/.local/state/vault-freeze/LOCK. Each writer looks for it before it writes and refuses if it is there.

My agent wrote the design on November 4 and I approved it. The line for the writers reads (translated): “every writer reads the flag and refuses; fixed message, non-zero exit.” The line for the commit hook: “flag exists ⇒ exit 1.” A coding agent wrote the eight checks. Four are Python and share this:

def is_frozen() -> bool:
    """旗標存在＝停寫期間；連 dangling symlink 也算。"""

    return os.path.lexists(freeze_lock())

(The docstring: “flag exists = writes stopped; a dangling symlink counts too.”) Four are shell. This is the whole commit hook:

#!/bin/sh
# P2-01 vault freeze: refuse every commit into the journal-git while the freeze flag exists.
# Covers journal.sh／fleet.sh／a direct `G commit` alike (`--no-verify` bypasses it — disclosed).
F="${VAULT_FREEZE_LOCK:-$HOME/.local/state/vault-freeze/LOCK}"
if [ -e "$F" ] || [ -L "$F" ]; then
  echo "pre-commit: commit refused (vault frozen): $F exists" >&2
  exit 1
fi
exit 0

Both versions handle the edge case people usually remember: a flag that is a symlink to nothing still counts. That is why it is lexists and not exists, and why -L sits next to -e.

What the report said

The second development round closed at 11:00 on November 7. From its report (translated, numbers as written):

tests/test_vault_freeze.py 28 passed

The one invalid mutant came from a stale baseline, and the report said so. One of the 28 tests has read-error in its name; it feeds the CLI a file descriptor that fails on read(), standard input, not the flag. I read the report as: the freeze works.

What the reviewer read

Each round goes to a reviewer agent that has not seen the development. Its review was committed at 11:04: BLOCKING, confidence 97%. On this point it ran nothing new. It read the patch, then the implementation of lexists in the interpreter the CLI actually uses, Python 3.12 (posixpath.py):

def lexists(path):
    """Test whether a path exists.  Returns True for broken symbolic links"""
    try:
        os.lstat(path)
    except (OSError, ValueError):
        return False
    return True

and wrote (translated):

Parent directory not searchable, or lstat fails with EACCES/EIO or similar: returns False. reject_frozen() lets it through, and rejections.record() goes on to create the directory and the lock and append to the jsonl.

This is a static counterexample confirmed from the patch, the actual interpreter implementation and the write order; under the constraints, no permission-fault script was added and run. The existing read-error test covers stdin EBADF, not a flag lookup error.

Allow only when it is positively confirmed that the flag does not exist; every other lookup error must refuse, and the error path must not fall back into the telemetry write.

lstat is the system call that answers “is there a directory entry here”. When it cannot answer, it says why: no such file, permission denied, I/O error. lexists has two return values, so it folds every reason into False, and False is the value that means “no flag, go ahead”. The shell test does the same. POSIX describes -e as: “True if pathname resolves to an existing directory entry. False if pathname cannot be resolved.” The Python docs say of os.path.exists that it “may return False if permission is not granted to execute os.stat() on the requested file, even if the path physically exists”; the entry for lexists doesn't repeat that, but the function above is all there is to it.

The flag was there the whole time. With the directory locked, the hook printed nothing and allowed the commit. With the directory open, it refused. Each command reported something true. The lookup failed and said so, the existence check turned the failure into False, and the hook read False as “not frozen”.

This has never happened on my machine. It needs a broken permission on a directory in my home folder, or a disk error. It is the case the switch exists for, though: the copy I'm protecting would run on a machine where something has already gone wrong.

What I got wrong

  • The design sentence had two outcomes. “Refuses if the flag exists” divides the world into exists and doesn't exist. The system call has a third answer, couldn't tell, and the sentence gave it nowhere to go. The code wrote down what the sentence said.
  • I had already been told. On November 4, three days earlier, a reviewer blocked the command that raises the flag for the same shape in two places, and a close relative of it in a third: a state file that could not be parsed was accepted as safe. One of the two (translated): “every non-zero launchctl print is treated as not loaded; a lookup error other than ‘no such service’ also skips the bootout.” Those three were fixed. The code that reads the flag was first written that afternoon, and the fix didn't carry over to it, because I fixed instances and wrote no rule.
  • It was in all eight. After the review I searched for the same check in the other writers. Every one had it: os.path.lexists in the four Python files, [ -e ] || [ -L ] (or [[ … ]]) in the four shell files. The review had named one function. Fixing that one would have left seven.

How the fix was checked

The third round, at 12:47, changed all eight checks to the same rule: lstat succeeds ⇒ frozen; lstat fails with ENOENT ⇒ go ahead; anything else ⇒ refuse with the error name. In Python:

    try:
        os.lstat(freeze_lock())
    except FileNotFoundError:
        return None
    except OSError as error:
        return errno.errorcode.get(error.errno or -1, "EUNKNOWN")
    except ValueError:
        return "ValueError"
    return "present"

New tests make the flag unreachable two ways, a directory with no permissions and a parent path that is a file, and expect a refusal at each of the eight places. Run against the old code first, the harness tests went (translated, numbers as written): “18 failed (16 cells write was not refused on a flag lookup error, wm telemetry 2 cells flag lookup error let a write change state; unlocked controls all passed).” Against the new code they passed. The round closed at 16:40 with 87 PASS / 0 FAIL on the probes and 102 of 102 mutants effective; the next fresh review passed it at 16:44, and the eight checks went live at 17:45.

The fix has a price, and the round report lists it. Shell has no portable way to get the errno from a failed lookup, so the four shell checks ask /usr/bin/stat and match its English error text. That is macOS-specific. If the wording changes, the checks see an error they don't recognise and refuse, so every shell writer stops until I fix the match. If the permission on that directory breaks for real, every write in the folder stops, and the only signal is stderr. That is what fail-closed means here. The next morning the scheduled jobs ran and wrote as usual.

In 3.9, 3.11 and 3.12 (which I ran) and 3.13 (whose source I read), pathlib.Path.exists() returned False only for a short list of errors (ENOENT, ENOTDIR, EBADF, ELOOP) and re-raised the rest. In 3.14 it calls os.path.exists() and returns False for all of them. The changelog entry, under 3.14.0a1: “Suppress all OSError exceptions from pathlib.Path.exists and is_*() methods, rather than a selection of more common errors.” The 3.14 documentation now says “False will be returned if the path is invalid, inaccessible or missing. Use Path.stat to distinguish between these cases.” The change is documented and the docs are accurate. I didn't find it in What's New in 3.14.

So a guard written as if Path(flag).exists(): refuse() on 3.13 would, by accident, refuse on a permission error: the exception stops the program before it writes, unless something above it catches the exception. On 3.14 the same line returns False and the write goes ahead. Nothing in the guard changed.

Node behaves like lexists: fs.existsSync() on the same path printed false (v24.9.0).

The rule

In a guard, only a positive “not there” opens the gate. In Python that means calling os.lstat (or os.stat) yourself and allowing only on FileNotFoundError. exists, lexists, isfile, Path.exists, [ -e ], [ -f ] and fs.existsSync each answer two of the three cases, and in a guard the third case goes to whichever side False means.

And when a reviewer finds the shape once, search for it everywhere before fixing the one they found. Between November 4 and 7 I had the same shape in ten places and a close relative of it in one more, and three of those eleven had already been caught and fixed.

Run it

checks/010/failopen.py takes any guard as a command. Exit 0 means “go ahead”, anything else means “refuse”, and {} in any argument is replaced by the flag path. It builds five flags in a temp directory: absent, present, a dangling symlink, a parent that is a symlink loop, and a parent with no permissions (skipped when running as root, since root ignores directory permissions). Before testing, it checks each one with os.lstat and stops if a fixture isn't what it claims to be. It runs six controls first and refuses to judge your guard if they don't come out as expected:

The same command against the fixed hook prints OK and exits 0. Both hooks are in the same directory: precommit_r2.sh before the fix, precommit_r3.sh after. Against Path(p).exists(follow_symlinks=False) it prints FAIL-OPEN on both 3.12 and 3.14: on 3.12 the symlink-loop flag gets through (ELOOP is on the old ignore list) and the permission case is refused only because the exception ends the process; on 3.14 both get through.

It is 77 lines. I broke it ten ways with checks/010/mutate.py; eight changed its verdict or exit status on the two hooks. The two that didn't, turning off the fixture self-check and not enforcing the controls, change nothing when the fixtures and controls are already right. They are there for a machine where they aren't.

Two limits. A guard that crashes only on the unreachable cases counts as refusing, which is right only if nothing above it catches the crash. I ran it on macOS only.
