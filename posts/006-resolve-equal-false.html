I keep my tasks in one Markdown file and change it through a small CLI that agents call. Last week I had an agent add a guard to that CLI. The rule was simple: a run that writes to the real task file must also use the real state directories, and a run pointed at test directories must not touch the real task file. Test harnesses set those directories through environment variables, so without the guard a test run with the wrong path could write to the file I actually use.

The spec was written by my agent; I never read that line. It said the target counts as production when it is the production file "after resolve" (translated from my notes). The coding agent implemented it in one line:

target_prod = taskforge.resolve() == PRODUCTION_TASKFORGE.resolve()

I never read that line, but the agents and the workflow were mine, so what follows is written as my mistake.

What the report said

The coding agent finished at 11:46. Its report:

1 failed, 358 passed, 5 deselected in 25.74s

The one failure was a test that had been red before the work started and had nothing to do with it. Then the mutation run:

Top-level command: `.venv/bin/python tools/run_w5_mutants.py` → rc 0, **49/49 killed**.

Two of the 49 mutants were on the guard. One replaced the check on the state directory with return False; the other replaced the line that ties the target to the directories with if False:. Both were killed. The test that killed the second one is called test_production_binding_resolved_aliases_every_host. It makes a symlink to the production file, calls the CLI through the symlink with test directories, and expects a refusal. It got one.

I read that as: the guard works, and it has been checked against aliases.

What the reviewer did

I send each round of this kind of work to a reviewer agent that has not seen the development. Its brief had a line for the guard: try to construct a call that writes the production task file with non-production directories, on either machine.

Seven minutes in, it ran this probe (temp prefix shortened to $S):

a = Path(s) / "case/Vault Dir/_taskMgt/TaskForge.md"
b = Path(s) / "case/vault dir/_taskmgt/taskforge.md"
print("exists lower:", b.exists())
print("resolve equal:", a.resolve() == b.resolve())

$S/case/Vault Dir/_taskMgt/TaskForge.md
$S/case/vault dir/_taskmgt/taskforge.md

The default macOS volume ignores case when it opens a file and keeps whatever case you typed in the path you hold. resolve() follows symlinks and removes ..; it handed back the lowercase string unchanged. Two strings, one file.

Its first attack, two minutes later, set up a stand-in production file in a temp directory and tried to mark a task done through a lowercase spelling of it:

alias samefile: True | resolve equal: False
lock keys equal: False
case-alias: rejected -> mutation id is not globally unique: 01ARZ3NDEKTSV4RRFFQ69G5FAV

A refusal. The reviewer read the message: it came from a different check, one that counts task ids, not from the guard. It switched to an operation that check doesn't cover, adding a task, and ran it as both machines:

[<desktop>] case-alias ADD with tmp roots: ACCEPTED rc0; production file now has the line: True | lock dir: ['e993f900', 'store.ho', 'store.lo']
[laptop] case-alias ADD with tmp roots: ACCEPTED rc0; production file now has the line: True | lock dir: ['e993f900', 'store.ho', 'store.lo']

That was 11:59, ten minutes after it started. The stand-in production file had the new line. The per-target lock file (e993f900…) had a name that a writer using the real spelling would not compute, because its key was a hash of the same string: sha256(str(taskforge.resolve())).

The reviewer's own severity note, paraphrased: this needs a deliberately configured test environment plus a mis-cased path; it is not something you hit by accident. My real task file was never written through this. The work was on a branch, and it merged later that day after the fixes below.

What I got wrong

  • I specified identity as a string. "After resolve" answers where symlinks and .. lead. It does not answer which file a path opens. The question the guard needed answered was the second one.
  • I took a test's name for its coverage. resolved_aliases_every_host built one kind of alias, a symlink, which is the one kind resolve() handles. The name said more than the test did.
  • I read 49/49 as "the guard is right". A mutant asks whether the tests notice when a line is deleted or switched off. Every mutant on the guard did that. None replaced the comparison with a different idea of what "the same file" means, and the mutants came from the same agent that wrote the comparison, so none would have.
  • The knowledge was already in the file. Fifty-six lines below the guard, in the same module, the same agent had written this for the record files:
    # On a case-insensitive volume, an uppercase argument can open a lowercase
# directory entry. Check the actual entry as well as the requested basename.
    That check had its own test (test_loader_rejects_filename_case_and_symlink) and its own mutant, killed. It was applied to record filenames and not to the one comparison that protected the production file.

The fix took two more rounds

Round two (12:10) switched the production check to os.path.samefile and keyed the per-target lock on the file's inode. The next fresh reviewer found the inode key moved: the CLI writes by writing a temp file and renaming it over the original, so every write produces a new inode. Its measurement:

per-target lock files after 2 mutations: 2

It also found that a second tool, which writes the same file and had not yet been updated, still used the old string key. While the CLI held its locks:

[UNPATCHED production ti] while wm holds locks -> ti key 743f968d1a9f | ti acquired after 0.00s

and that tool's 18 tests skip themselves when they find the old version, so a CI run in that window would have been green. Both programs also take one store-wide lock at a fixed path, which is what kept them serialized; the reviewer said so, and I have no evidence the two ever wrote at the same time.

Round three (12:51) keyed the lock on the case-folded resolved path and kept samefile for the production check, with case-folding only as a fallback when the file does not exist yet. That merged at 13:10.

Case-folding is still a string. I checked the two ways it can be wrong. A path whose é is spelled in decomposed Unicode (NFD) opens the same file on APFS and does not compare equal after casefold(). And on a case-sensitive volume, Main.md and main.md are two files that case-fold to one key (that direction only over-locks). The reviewer judged the first one unreachable for this tool because its real paths are ASCII. I agree, and I'm noting it because it is the same kind of answer as the one that failed.

Reproducing it

Any Mac with a default (case-insensitive) volume. Python 3.12 at the time, 3.14.6 today; same result.

python3 -c 'import os; from pathlib import Path as P; a = P("/tmp/demo6/Vault/Tasks/Main.md"); b = P("/tmp/demo6/vault/tasks/main.md"); print(b.exists(), a.resolve() == b.resolve(), os.path.samefile(a, b)); print(b.resolve())'

What generalises

  • To ask "is this that file", ask the filesystem. os.path.samefile, or compare (st_dev, st_ino) from os.stat. resolve(), realpath, casefold() and Unicode normalisation each remove one way of spelling a path differently; the volume decides which spellings open the same file, and it can be different on the next machine.
  • Key a lock on a name you chose, not on how the caller spelled the target. One fixed lock path per resource held up here; the key derived from the caller's path split twice, by case and then by inode.
  • A guard needs a test written by someone who wants it to fail. Mutation testing checks the tests against the code's own idea. To check the idea, give the guard a list of spellings built without it, or give it to a reviewer whose job is to get through.
  • A refusal is evidence about the check that refused. Read the message before counting it as the guard working.

The check

alias_check.py takes any predicate f(candidate, protected) -> bool and asks it about spellings of one file and about files that are not it. Which spellings open the file is known by construction (a fresh directory holding exactly one file), not by calling samefile, so the checker does not share an answer with the predicate it checks. Spellings that this volume does not open are skipped and said so.

$ python3 alias_check.py guards.py:resolve_eq
ok    exact               -> True  (want True)
ok    symlink             -> True  (want True)
ok    symlinked parent    -> True  (want True)
ok    dot-dot             -> True  (want True)
MISS  hard link           -> False (want True)
MISS  case                -> False (want True)
MISS  unicode (NFD)       -> False (want True)
ok    sibling             -> False (want False)
ok    byte-identical copy -> False (want False)
verdict: 3 wrong

Exit 1. With guards.py:samefile every answer is right and it exits 0. controls.py runs it against seven predicates whose right answers are known (the first-round guard is the known positive), and mutate.py breaks the checker eleven ways. Ten are caught. The one that survives keeps a spelling without first checking that the volume opens it. On a default macOS volume that changes nothing, so the controls cannot see it; on a case-sensitive volume it turns a correct samefile predicate into a FileNotFoundError and a false MISS. I tested that on a case-sensitive disk image. My controls only run on one kind of volume, and that is the gap.
